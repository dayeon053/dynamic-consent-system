# 유즈케이스 최종

# **1단계. 요구사항 분석**

## **1-1. 시스템 개요**

본 시스템은 국내 주요 서비스(카카오, 네이버 등)의 개인정보처리방침을 자동으로 수집·분석하여 위험도를 산출하고 사용자에게 알림으로 제공하는 개인정보 위험도 모니터링 시스템이다. 기존 동의ON 어플리케이션의 UI 디자인을 재활용하되, Kotlin 기반 Android 앱으로 새로 개발하며 크롤링 봇 백엔드와 오버레이 팝업 기능을 신규 구축하여 하나의 앱 안에서 모든 기능이 동작하는 구조로 구성한다.

## **1-2. 배경 및 문제 정의**

현재 사용자는 자신이 동의한 개인정보 약관이 언제 바뀌는지, 현재 얼마나 위험한 상태인지 알 방법이 없다. 도출된 핵심 방향은 다음과 같다.

- 필수동의 및 선택동의 항목 목록은 기업 약관에 고정된 정보이므로 봇이 자동으로 수집할 수 있다.
- 사용자의 선택동의 체크 현황은 기업과 연동하여 가져오는 것을 목표 시나리오로 삼는다. 단, 실제 기업 서버와의 실시간 연동은 기술적·정책적으로 현재 불가능하므로, 개발 단계에서는 각 기업별 선택동의 체크 현황을 우리 DB에 임의로 구성하여 연동된 것처럼 동작하는 방식으로 구현한다. 즉 동의 데이터는 우리 DB에서 관리하고, 팝업 감지와 위험도 표시 대상은 실제 상용 앱(카카오톡 등)으로 하는 구조다. 이는 연동의 한계를 인정하되 서비스 취지를 최대한 구현하는 접근이다.
- 자동 수집된 데이터와 위험도 점수를 매일 갱신하고 누적하는 것 자체가 자산이다.

## **1-3. 기능 요구사항**

### **[F1] 크롤링 봇 - 필수동의 및 선택동의 항목 자동 수집**

- 국내 주요 서비스의 개인정보처리방침 페이지를 자동으로 접근하여 필수동의 및 선택동의 항목 목록을 수집한다. 초기에는 5~10개 기업으로 시작하여 안정성 검증 후 50개 이상으로 확장한다.
- 수집 주기는 1일 1회 자동 실행이다.
- 매일 수집한 약관 텍스트를 전일 DB 저장본과 비교하여 변경 여부를 자동 감지한다. 변경이 감지되면 위험도를 재산출하고 알림 플래그를 설정한다. 변경 감지는 별도 작업이 아니라 크롤링 봇 안에 전일 대비 비교 로직을 추가하는 방식으로 구현한다.
- 수집 방식은 단계적으로 고도화한다.
    
    **1단계 (초기 구현):** 개인정보처리방침 웹 페이지를 크롤링하여 텍스트를 수집하고, LLM으로 필수동의 및 선택동의 항목을 파싱한다. 대부분의 대형 서비스는 개인정보처리방침 안에 수집 항목, 제3자 제공 내역, 보관 기간이 포함되어 있어 이 방식으로 커버 가능하다.
    **2단계 (고도화):** 개인정보처리방침만으로 필수/선택동의 구분이 명확하지 않은 기업의 경우, 봇이 직접 앱 회원가입 화면에 접근하여 동의 화면을 캡처하고 OCR로 텍스트를 추출하는 방식을 추가 적용한다. 실제 동의 화면에서 필수/선택 구분이 가장 명확하게 드러나기 때문이다. 봇 탐지 우회가 필요한 경우 이 방식을 적용한다.
    
- 개인정보처리방침 크롤링
    
    개인정보처리방침이 변경됐는지 알려면 "어제 내용"이랑 "오늘 내용"을 비교해야 한다. 이 비교 자체가 크롤링으로 매일 내용을 긁어와야 가능하다.
    
    흐름을 보면 이렇다.
    
    > 1일차 크롤링 → DB에 약관 내용 저장
    2일차 크롤링 → 오늘 긁어온 내용과 DB의 어제 내용 비교
    다르면 → 변경 감지 → 위험도 재산출 → 알림 플래그 설정
    > 
    
    즉 **변경 감지 자체가 크롤링의 부산물**이다. 매일 약관을 긁어오는 것만 하면 변경 여부는 자동으로 알 수 있다. 별도 작업이 추가되는 게 아니라 크롤링 봇 안에 "어제랑 달라졌냐" 비교 로직만 추가하면 된다.
    

### **[F2] 위험도 자동 산출**

- 크롤링 봇이 수집하고 파싱한 필수동의 및 선택동의 항목 데이터를 기반으로 봇 파이프라인 내에서 자동으로 위험도 공식(Risk Score = DS + (ES × TF × PC × AI) × 2)을 적용하여 기업별 위험도 점수를 산출한다. 위험도는 필수동의 + 사용자가 실제 체크한 선택동의를 기준으로 산출하며, 사용자가 선택동의를 철회할 경우 실시간으로 반영된다.
- 전체 위험도(워스트 케이스)는 별도로 산출하지 않는다. 초기에는 경각심 제공 목적으로 워스트 케이스를 팝업 및 대시보드에 표시하는 방안을 검토하였으나, 각 기업별 DB를 임의로 구성하여 사용자 맞춤형으로 보여주는 구조라면 워스트 케이스보다 개인 맞춤 위험도를 보여주는 것이 서비스 취지에 더 부합한다고 판단하였다. 또한 사용자가 선택동의를 하나씩 철회할 때 위험도가 낮아지는 흐름 자체가 경각심 제공 역할을 충분히 대신한다.
- 필수동의 위험도 역시 별도로 산출하지 않는다. 초기에는 필수동의가 거부할 수 없는 항목임에도 불구하고 위험이 존재한다는 점을 사용자에게 명확히 알리기 위해 별도 지표로 제공하는 방안을 검토하였다. 그러나 필수동의는 개인 위험도 산출 기준에 이미 포함되어 있어 중복이고, 사용자 입장에서 "필수동의만의 위험도"를 별도로 보여주는 것이 실질적인 행동 변화로 이어지기 어렵다고 판단하였다.
- 산출 결과는 DB에 날짜별로 누적 저장한다.

### **[F3] 오버레이 팝업 - 앱 실행 감지 및 경고**

- Android 환경에서 특정 앱(카카오톡 등) 실행을 감지하면 해당 기업의 개인 맞춤 위험도 등급을 팝업으로 표시한다. 감지 대상은 실제 상용 앱이며, 앱의 패키지명(예: com.kakao.talk)을 우리 DB의 기업 정보와 매핑하는 방식으로 구현한다.
- 팝업은 간결함을 최우선으로 설계한다. 위험도 5단계 등급 텍스트(예: 보통, 매우 위험)와 앱 내 상세보기 버튼, 이 두 가지만 표시한다. 내용이 많으면 사용자가 습관적으로 닫기를 누르게 되어 경각심 효과가 떨어지기 때문이다.
- iOS는 시스템 정책상 팝업 구현이 불가능하므로 Android 전용으로 개발한다.

### [F4] 기업별 위험도 대시보드 및 개인 위험도 산출

- 위험기관리스트에서 사용자의 개인 맞춤 위험도 기준으로 기업들을 높은 순으로 확인할 수 있다. 선택동의 체크/해제 시 위험도와 순위가 실시간으로 반영되어 현재 나에게 가장 위험한 기업이 무엇인지 파악할 수 있다.

![image.png](image.png)

- 위험 등급은 매우 안전~매우 위험 5단계로 표시한다.
- 기업 선택 시 상세 화면에서 아래 탭을 확인할 수 있다.
    - **동의 세부사항 탭**: 필수동의 및 선택동의 항목 목록과 스위치(체크/해제). 선택동의 항목을 체크/해제하면 개인 위험도가 실시간으로 반영된다.
    - **위험도 탭**: 위험도 점수, 산출식(DS + (ES × TF × PC × AI) × 2), 5대 변수 상세 분석 내용.
    - **제3자 제공 탭**: 제3자 제공 흐름도 (추후 구현).
    - **동의 변경 내역 탭**: 사용자가 해당 기업에 대해 언제 어떤 동의를 체크/해제했는지 시간순으로 기록된 이력.
    - **정보 탭**: 기업 기본 정보 및 ISMS-P 등 보안 인증 현황.

- 날짜별 위험도 추이 그래프와 전일 대비 변동 표시(▲▼)는 데이터 누적 및 UI 구현 리소스를 고려하여 추후 구현한다. 변경 이력은 데이터가 충분히 누적된 이후 추후 구현한다.

#### **[팀 내부 검토 사항]**

**Q1. 날짜별 추이 그래프는 DB에 데이터가 쌓이면 어차피 가능한 거 아닌가?**
데이터 자체는 봇이 매일 DB에 누적 저장하므로 백엔드 관점에서는 어렵지 않다. 그러나 안드로이드 앱 화면에 선 그래프를 구현하려면 MPAndroidChart 등 외부 라이브러리 연동과 UI 작업이 별도로 필요하고, 개발 초기에는 데이터가 1~2개뿐이라 그래프 자체가 의미없게 보일 수 있다. 전일 대비 변동 표시(▲▼)도 동일한 이유로 추후 구현으로 분류한다.

**Q2. 변경 이력도 추후 구현으로 빼도 되는가?**
변경 이력은 데이터가 충분히 쌓여야 의미가 생기는 기능이다. UI 자체는 단순한 목록이라 구현이 어렵지 않으나 개발 초기에는 보여줄 데이터가 없으므로 추후 구현으로 분류한다.

**Q3. 날짜별 추이 그래프와 변경 이력은 뭐가 다른가?**

둘 다 데이터가 누적되어야 의미가 생기는 기능이지만 성격이 다른 별도 기능이다.

| 구분 | 형태 | 내용 |
| --- | --- | --- |
| 날짜별 추이 그래프 | 시각화 (선 그래프) | 위험도 점수의 시간별 흐름. 예: 카카오톡 위험도가 1월 31.5점 → 2월 35점 → 3월 38점으로 변화하는 흐름 |
| 변경 이력 | 텍스트 목록 | 기업의 개인정보처리방침이 변경되었을 때 언제, 무엇이, 어떻게 바뀌었는지 기록. 사용자의 동의 변경 이력과는 별개다. 예: "2025년 3월 1일 - 카카오톡 마케팅 수신 동의 항목 추가 / 위험도 31.5 → 38.2" |

**Q4. F4와 F5를 왜 나눴는가? 합치는 게 맞지 않나?**
원래 F4는 봇이 자동 수집한 기업별 위험도 대시보드, F5는 사용자가 직접 선택동의를 입력해 개인 위험도를 산출하는 기능으로 분리되어 있었다. 그러나 개인 위험도 산출이 위험기관리스트와 기업 상세 화면 모두에서 선택동의 체크/해제 시 실시간으로 반영되는 구조로 확정되면서 F5가 F4 안에 자연스럽게 포함되었다. 따라서 두 기능을 하나로 합쳐 F4로 통합하였다.

### **[F5] 처리방침 변경 알림**

- 크롤링 봇이 전일 대비 약관 텍스트 변경을 감지하면 위험도를 재산출하고 사용자에게 푸시 알림을 발송한다.
- 알림에는 변경된 기업명과 위험도 변화 내용을 포함한다.
- 알림 수신 후 앱 홈 화면의 공지사항 탭에서 변경된 처리방침의 구체적인 위험성과 주의사항을 확인할 수 있다.

### **[F6] 제3자 제공 흐름도 조회**

- 기업 상세 화면 내 별도 탭에서 내 개인정보가 어떤 파트너사·외부 서버로 흘러가는지 시각화된 흐름도로 확인할 수 있다.
- 현재 디자인은 완성되어 있으나 로직 및 기능 구현은 완료되지 않았다. 앱에서 처음부터 개발해야 하는 기능이다. 추후 구현 과제로 분류한다.
- 사용자 입장에서 내 정보가 어디로 흘러가는지 시각적으로 파악할 수 있다는 점에서 서비스 차별점이 된다.

#### **[팀 내부 검토 사항]**

**Q1. 제3자 제공 흐름도를 아예 빼는 건 어떤가?**
현재 디자인만 완성된 상태이며 로직 및 기능 구현은 되어 있지 않다. 앱에서 처음부터 개발해야 하는 기능이다. 다만 사용자 입장에서 내 정보가 어디로 흘러가는지 시각적으로 보여준다는 점에서 서비스 차별점이 되고, 한이음 발표에서도 어필할 수 있는 기능이므로 완전히 제외하지 않고 추후 구현 과제로 분류하기로 결정하였다. 기업 상세 화면 내 별도 탭으로 배치하여 메인 화면을 복잡하게 만들지 않는 방식으로 구성한다.

## **1-4. 비기능 요구사항**

- **자동화**: 크롤링과 위험도 산출은 사람 개입 없이 매일 자동 실행되어야 한다.
- **확장성**: 크롤링 대상 기업 수를 쉽게 추가할 수 있어야 한다.
- **Android 전용**: 오버레이 팝업 기능은 Android 환경만 지원한다. iOS는 시스템 정책상 팝업 구현이 불가능하므로 제약사항으로 명시한다.
- **데이터 누적**: 위험도 데이터는 날짜별로 삭제 없이 누적 보관한다. 날짜별 추이 그래프와 변경 이력은 데이터가 충분히 누적된 이후 추후 구현한다.
- **제약사항 인정**: 실제 기업 서버와의 선택동의 실시간 연동은 기술적·정책적으로 불가능하다. 이를 해결하기 위해 각 기업별 선택동의 체크 현황을 우리 DB에 임의로 구성하여 연동된 것처럼 동작하는 방식으로 구현한다.

## **유즈케이스 목록**

### **UC-01. 앱 실행 시 위험도 팝업 확인**

- **액터**: 일반 사용자
- **설명**: 사용자가 Android 기기에서 카카오톡 등 대상 앱을 실행할 때 해당 기업의 최신 위험도 등급이 팝업으로 표시된다.
- **전제조건**: Android 기기에 동의ON 앱이 설치되어 있고 권한이 허용된 상태
- **기본 흐름**: 대상 앱 실행 감지 → 해당 기업의 개인 맞춤 위험도 조회 → 팝업 표시(위험도 5단계 등급 텍스트 + 상세보기 버튼)
- **제약**: iOS 불가, 실제 앱의 설정 화면으로 이동 불가(warning 제공만 가능)

### **UC-02. 위험기관리스트 및 기업 상세 화면 조회**

- **액터**: 일반 사용자
- **설명**: 사용자가 앱에서 개인 맞춤 위험도 기준으로 기업들을 높은 순으로 확인한다. 선택동의 체크/해제 시 위험도와 순위가 실시간으로 반영된다.
- **기본 흐름**: 앱 실행 → 기관 탭 선택 → 위험기관리스트에서 개인 맞춤 위험도 높은 순으로 기업 목록 조회 → 특정 기업 선택 → 위험도 간략 정보 확인 → 자세히 보기 버튼 클릭 → 기업 상세 화면 위험도 탭으로 진입 → 각 탭(동의 세부사항·위험도·제3자 제공·동의 변경 내역·정보) 확인 가능

### **UC-03. 선택동의 체크/해제를 통한 개인 위험도 실시간 반영**

- **액터**: 일반 사용자
- **설명**: 사용자가 특정 기업에 대해 선택동의 항목을 체크/해제하면 개인 위험도가 실시간으로 반영된다.
- **전제조건**:선택동의 항목 목록은 봇이 자동 수집한 상태. 사용자의 실제 체크 여부만 자동 수집 불가
- **기본 흐름**: 기업 상세 화면 진입 → 동의 세부사항 탭에서 선택동의 항목 체크/해제 → 개인 위험도 실시간 반영

### **UC-04. 크롤링 봇 자동 수집 (시스템 자동 실행)**

- **액터**: 크롤링 봇
- **설명**: 크롤링 봇은 Spring Boot 서버 내 스케줄러 모듈로 구현된다. 약관 텍스트 수집부터 위험도 산출, DB 저장, 변경 감지까지 전 과정을 자동으로 처리하며 사람이 개입하는 구간이 없다. Spring Boot 서버는 봇 실행 외에 앱에 데이터를 전달하는 API 역할도 함께 담당한다.
- 기본 흐름: 스케줄러 트리거 → 기업별 약관 페이지 접근 → 필수동의 및 선택동의 항목 텍스트 수집 (1단계: 개인정보처리방침 웹 크롤링 + LLM 파싱 / 2단계: 회원가입 화면 캡처 + OCR - 추후 구현) → 5대 변수 자동 매핑 → 개인 위험도 산출 (필수동의 + 사용자가 실제 체크한 선택동의 기준) → DB 저장 → 오늘 수집 내용과 전일 DB 저장본 텍스트 비교 → 변경 감지 시 위험도 재산출 후 알림 플래그 설정
- 변경 감지 시 위험도 재산출 후 알림 플래그 설정 → 이거 자세한 설명
    
    이건 **기업의 약관 자체가 바뀌었을 때** 모든 사용자에게 보내는 알림이다. 개인별 선택동의 현황이랑은 무관하다.
    
    예를 들면 이런 거다.
    
    > "카카오톡이 개인정보처리방침을 변경했습니다. 위험도가 31.5점 → 38.2점으로 상승했습니다."
    > 
    
    카카오톡을 쓰는 모든 사용자에게 동일하게 가는 공통 알림이고, 앱을 열었을 때 뜨는 오버레이 팝업과는 별개다.
    
    ---
    
    **두 가지를 정리하면 이렇다.**
    
    | 구분 | 트리거 | 대상 | 내용 |
    | --- | --- | --- | --- |
    | 오버레이 팝업 | 사용자가 특정 앱 실행할 때 | 해당 앱 실행한 사용자 | 현재 이 기업 위험도 등급 |
    | 변경 알림 (푸시) | 기업 약관이 바뀌었을 때 | 전체 사용자 공통 | 약관 변경 + 위험도 점수 변화 |
    
- 우리 위험도 공식이 개인정보처리방침이 바뀌면 위험도가 바뀔 수 있는 구조임?
    
    위험도 공식을 다시 보면
    
    **Risk Score = DS + (ES × TF × PC × AI) × 2**
    
    5개 변수 중에서 개인정보처리방침이 바뀌면 실제로 영향받는 변수가 있는지 따져보면 이렇다.
    
    | 변수 | 약관 변경 시 바뀔 수 있나 | 이유 |
    | --- | --- | --- |
    | DS (데이터 민감도) | **가능** | 수집 항목이 추가되면 민감도 올라감 (예: 위치정보 신규 수집) |
    | ES (노출 범위) | **가능** | 제3자 제공 범위가 늘어나면 점수 올라감 |
    | TF (경과 시간) | 거의 안 바뀜 | 보관 기간 변경은 드물지만 가능하긴 함 |
    | PC (목적 명확성) | **가능** | 목적 표현이 포괄적으로 바뀌면 1.0 → 1.5로 변함 |
    | AI (AI 위험계수) | **가능** | AI 프로파일링 신규 도입 명시 시 1.0 → 1.5로 변함 |
    
    ---
    
    **결론적으로 구조상 위험도가 바뀔 수 있다.** DS, ES, PC, AI 네 개 변수가 전부 약관 텍스트에서 읽어오는 값이라서, 약관이 바뀌면 변수값이 바뀌고 점수도 바뀐다.
    
    카카오톡 친구 위치 공유 사례가 딱 이 케이스다. 위치 공유 기능 추가 → DS 상승 + ES 상승 → 위험도 점수 올라간다.
    

### **UC-05. 처리방침 변경 알림 수신**

- **액터**: 일반 사용자
- **설명**: 특정 기업의 개인정보처리방침이 변경되어 위험도가 상승하면 사용자에게 푸시 알림을 발송한다. 이는 기업 약관 자체가 바뀌었을 때 전체 사용자에게 공통으로 발송되는 알림으로, UC-01 오버레이 팝업과는 별개다.
- **기본 흐름**: 봇이 변경 감지 → 서버에서 위험도 재산출 → 전일 대비 점수 변화 확인 → 푸시 알림 발송 (변경된 기업명 + 위험도 점수 변화 내용 포함) → 사용자 앱 홈 화면 공지사항 탭에서 상세 확인

### **UC-06. 크롤링 대상 기업 관리 (관리자)**

- **액터**: 관리자
- **설명**: 관리자가 크롤링 대상 기업을 추가하거나 삭제하고 수집 상태를 점검한다.
- **기본 흐름**: 관리자 콘솔 접근 → 기업 URL 및 약관 페이지 경로 등록 → 테스트 크롤링 실행 → 정상 수집 확인 → 스케줄 등록

### **UC-07. 제3자 제공 흐름도 조회**

- **액터**: 일반 사용자
- **설명**: 사용자가 특정 기업의 기관 상세 화면에서 내 개인정보가 어떤 파트너사·외부 서버로 흘러가는지 시각화된 흐름도로 확인한다. 현재 디자인은 완성되어 있으나 로직 및 기능 구현은 완료되지 않았다. 추후 구현 과제로 분류한다.
- **전제조건**: 해당 기업의 개인정보처리방침 내 제3자 제공 내역이 크롤링 봇을 통해 수집되어 있어야 함
- **기본 흐름**: 기관 상세 화면 진입 → 제3자 제공 탭 선택 → 내 개인정보가 어떤 파트너사·외부 서버로 흘러가는지 시각화된 흐름도로 확인

    좋은 고민이다. 정리해줄게.

    **결론부터: 가상 사용자 만들 필요 없다.**
    
    "연동됐다치고" 개발하는 방식은 실제 연동 대신 **DB에 더미 데이터를 넣어두는 것**이다. 사용자를 만드는 게 아니라 데이터를 만드는 거다.
    
    ---
    
    **구체적으로 어떻게 개발하냐**
    
    흐름을 보면 이렇다.
    
    실제 연동이 된다면 카카오 서버에서 "이 사용자가 마케팅 동의 체크했음"이라는 데이터를 받아와야 한다. 근데 그게 불가능하니까, 대신 우리 DB에 아래처럼 데이터를 직접 심어두는 거다.
    
    ```
    사용자 ID: user_001
    기업: 카카오톡
    필수동의: [이름, 전화번호, 기기정보] → 체크됨
    선택동의: [마케팅 수신 → 체크됨, 위치정보 → 체크됨, 행태정보 → 체크 안 됨]
    ```
    
    앱은 이 DB에서 데이터를 읽어와서 보여주는 거다. 실제로 카카오 서버와 통신하는 게 아니라 우리 서버 DB에 있는 데이터를 보여주는 것뿐이라 개발 자체는 어렵지 않다.
    
    ---
    
    **팝업을 개인맞춤형으로 한다는 게 개발상 의미하는 것**
    
    팝업에 "카카오톡 위험도: 위험 (31.5점)"을 띄울 때, 전체 위험도(워스트 케이스)가 아니라 이 사용자의 실제 체크 기준으로 산출한 개인 위험도를 보여주는 거다. 그러려면 앱 실행 시 해당 사용자의 선택동의 체크 현황을 DB에서 조회해서 위험도를 실시간 산출해야 한다.
    
    ---
    
    **개발 단계 정리**
    
    | 단계 | 내용 |
    | --- | --- |
    | 1 | DB에 기업별 필수/선택동의 항목 테이블 설계 |
    | 2 | 로그인한 사용자별 선택동의 체크 현황 테이블 설계 |
    | 3 | 앱에서 사용자가 직접 선택동의 체크/해제 입력 |
    | 4 | 입력값 기반으로 개인 위험도 실시간 산출 |
    | 5 | 팝업 실행 시 해당 사용자 위험도 조회해서 표시 |
    
    3번이 핵심이다. 실제 카카오 서버에서 받아오는 게 아니라 사용자가 앱 안에서 직접 "나 마케팅 동의 했어요"를 입력하면 그걸 DB에 저장하고 위험도 계산에 쓰는 방식이다. 이게 바로 지금까지 얘기한 "사용자가 실제 체크 여부를 직접 입력"하는 방식이고, 한계를 인정하되 개발은 완성하는 현실적인 접근이다.
    
- db에 박아두면 카카오톡같은 기업도 가상으로 만들어서 테스트 해야하는거야? 아니면 애뮬레이터로 하면 진짜 카카오톡 대상으로도 되는거야?
    
    결론부터 명확하게 말씀드리면, **가상의 카카오톡 앱을 따로 만들 필요가 전혀 없습니다! 에뮬레이터나 실제 스마트폰에 깔려 있는 '진짜 카카오톡 앱'을 대상으로 완벽하게 테스트하고 개발할 수 있습니다.**
    
    그 이유와 정확한 작동 원리를 이해하기 쉽게 정리해 드릴게요.
    
    ### 1. 진짜 앱을 대상으로 작동하는 원리 (패키지명 인식)
    
    안드로이드에서 '어떤 앱이 실행되었는지' 감지하는 것은 그 앱의 고유한 패키지명(Package Name)을 통해 이루어집니다.
    
    - 예: 실제 카카오톡 앱의 패키지명은 `com.kakao.talk` 입니다.
    
    **[앱 실행 감지 및 팝업 흐름]**
    
    1. 사용자가 스마트폰(또는 에뮬레이터)에서 **'진짜 카카오톡'** 아이콘을 누릅니다.
    2. 안드로이드 OS가 "지금 `com.kakao.talk`가 실행됐어!" 라고 신호를 줍니다.
    3. 백그라운드에서 돌고 있던 **우리 '동의ON' 앱**이 이 신호를 낚아챕니다.
    4. 동의ON 앱은 카카오톡 서버가 아니라, **우리 서버 DB**에 물어봅니다. *"우리 DB에 저장된 user_001의 카카오톡(com.kakao.talk) 선택동의 내역이랑 위험도 점수 가져와!"*
    5. 가져온 데이터를 바탕으로 방금 켜진 **진짜 카카오톡 화면 위로** 동의ON의 오버레이 팝업을 띄웁니다.
    
    즉, **사용자의 동의 데이터만 우리 DB에 가상으로 만들어둔 것일 뿐, 감지하고 팝업을 띄우는 대상은 실제 상용 앱(카카오, 네이버 등)입니다.**
    
    ### 2. 어떻게 테스트해야 할까? (에뮬레이터 vs 실기기)
    
    - **실제 스마트폰 테스트 (강력 추천):** 안드로이드 개발 시, 본인 또는 팀원의 실제 안드로이드 폰을 PC에 연결해서 테스트하는 것이 가장 좋습니다. 이미 폰에 카카오톡, 네이버, 쿠팡 등이 깔려 있으니, 동의ON 앱만 설치해두고 평소처럼 카카오톡을 켜보면 바로 팝업이 뜨는지 확인할 수 있습니다.
    - **에뮬레이터 테스트:** 에뮬레이터로 하려면, Google Play Store가 포함된 에뮬레이터(AVD) 이미지를 생성한 뒤, 거기에 카카오톡 앱을 직접 다운로드 받거나 카카오톡 APK 파일을 구해 설치해두고 테스트하면 됩니다.
    
    ### 💡 안드로이드 개발 시 꿀팁 (꼭 알아두어야 할 권한)
    
    이 기능을 실제로 구현하려면 안드로이드에서 두 가지 강력한 권한을 사용자(또는 테스터)에게 허용받아야 합니다. 이 부분을 미리 고려해서 개발하세요.
    
    1. **앱 실행 감지 권한:** `UsageStatsManager` (사용 정보 접근 권한) 또는 `Accessibility Service` (접근성 서비스) 권한이 필요합니다. 어떤 앱이 켜졌는지 훔쳐보는 기능이기 때문에 권한 승인이 필수입니다.
    2. **오버레이 팝업 권한:** `SYSTEM_ALERT_WINDOW` (다른 앱 위에 그리기) 권한이 있어야, 실행된 카카오톡 화면 위에 동의ON 팝업을 강제로 덮어씌워서 보여줄 수 있습니다.
    
    **요약하자면:** 카카오톡 같은 타사 앱을 가짜로 만들 필요 없습니다. **"데이터는 가짜(우리 DB), 대상 앱은 진짜(실제 카카오톡)"** 구조로 개발하시면 됩니다. 실제 앱의 패키지명만 우리 DB의 기업 정보와 매핑해두면 완벽하게 연동된 것처럼 작동합니다!
